# .har — Agent Harness (CLI / library profile)

This directory is the **agent harness** for `@osfactory/otel-hook`. It lets AI
coding agents work in isolated git worktrees and run this repository's real
check pipeline.

Generated by [`har`](https://github.com/os-factory/har) `1.0.0-rc.2` with
`--profile cli`, then adapted. Run `har env maintain` when the stack changes.

**The harness is how you run this project in a slot.** Launch to get a worktree
with Node and `npm ci`; do not invent a parallel install path. If a harness
command fails, fix the harness or report it.

This package is a **library and CLI**, not a web app. There is no Docker Compose
stack, no preview URL, and no PM2 process. "Agent usable" means the built
`otel-hook` binary starts and lists providers.

## Quick start

```bash
har env launch 1
har env verify 1              # typecheck, build, fixture provenance
har env verify 1 --full       # + lint, vitest (unit/e2e/parity/packaging), CLI smoke
har env teardown 1
```

In Cursor with HAR MCP configured: `har_launch_environment`, `har_run_verification`, `har_teardown_environment`.

**Shell shims** (same runtime — each `./.har/*.sh` forwards to `har env`, with a pinned `npx @osfactory/har` fallback):

```bash
./.har/setup-infra.sh          # no-op (HARNESS_INFRA_SERVICES is empty)
./.har/launch.sh 1
./.har/verify.sh 1
./.har/verify.sh 1 --full
./.har/teardown.sh 1
```

## Verification contract

Stages match CI (`.github/workflows/ci.yml`) and `npm run check`.

| Mode | Command | Stages |
|------|---------|--------|
| Quick | `har env verify <id>` | `typecheck`, `build`, `fixtures-validate` |
| Full | `har env verify <id> --full` | those, plus `lint`, `unit-tests` (`npm test`), `readiness` (built CLI `--version` + `providers --json`) |

`unit-tests` is named for the HAR kind; the command is the full Vitest run (unit, e2e, parity, packaging). E2E drives `dist/cli.js`, so `build` always runs first.

No runtime services, seed, or credentials are required. Schema-only / no-seed is enough because this library has no database.

Use `har env launch 1 --no-worktree` only when working in the repo root.

## Run history

Every entry point — `./.har/*.sh`, `har env …`, MCP — writes records under the main checkout `.har/runs/YYYY-MM-DD/`.

With git worktree slots, verification runs code in the worktree but run JSON stays in the main repo `.har/runs/`. Each record includes `workDir` when a slot is active.

## For coding agents

**Start here:** [`AGENTS.md`](../AGENTS.md) at the repo root, then [`.har/CLAUDE.agent.md`](./CLAUDE.agent.md).

Prefer HAR MCP tools or `har env …` for launch, verify, and teardown. Use `./.har/*.sh` only when the CLI is not installed.

Work in the isolated git worktree created by launch. Use `./.har/agent-cli.sh <id> exec ...` to run ad-hoc project commands in that work dir.

Do not start Docker for this repository. Shared infra is unused (`HARNESS_INFRA_SERVICES` is empty).

## Port & shared services (CLI profile)

This profile has **no PM2 app ports** and **no Docker services**. Port variables in `harness.env` exist only so the schema stays valid; nothing in this package binds them.

### Port allocation

| Layer | Scope | Rule |
|-------|-------|------|
| Frontend / API | Unused | Defaults in `harness.env` are not read by tests or the CLI |
| Shared Docker | Unused | `HARNESS_INFRA_SERVICES` is empty; `setup-infra.sh` starts nothing |

### Shared vs per-slot

| Resource | Model | Configuration |
|----------|-------|---------------|
| Application code | Isolated git worktree per slot | `HARNESS_USE_WORKTREE=true` |
| Node toolchain | Per slot, via launch | `HARNESS_ECOSYSTEM=node`, `HARNESS_INSTALL_CMD=npm ci` |
| Docker / Postgres / Redis | Not used | empty `HARNESS_INFRA_SERVICES` |

### Do not

- Add a database or compose service unless the library itself gains that dependency
- Hardcode collector URLs in tests — exporters are injected
- Treat a passing typecheck as "agent usable"; full verify must run the built CLI

## Maintaining this harness

When the project stack changes (new scripts, extra check stages, env vars):

```bash
har env maintain
```

Customize through the contract — config (`harness.env`), stages (`stages.json` +
`stages/`), hooks (`hooks/`), plugins (`plugins/`). The `*.sh` files at `.har/`
root are generated shims: don't edit them. `har env doctor` validates the result.

## Session lifecycle

Every `launch` starts a **fresh session**: a new git worktree from the **main
checkout's current HEAD** at
`~/worktrees/<base-branch>-<sha4>-har-agent-<id>-<rand4>`, on a branch of the same name.
Switch that checkout to your intended base before launch. The session is recorded in
`.har/slots/agent-<id>.json`. Make ALL file edits under the work dir printed by launch,
never in the main checkout.

- Occupied slots always block a new launch: `har env complete <id>` (or `teardown <id>`),
  then `har env launch <id>`.
- `teardown` removes the worktree but **keeps the session branch**.
- If launch fails after creating a worktree/env file, resume with `har env launch <id> --resume`.
- `har env complete <id>` finishes a session: full verify, then teardown — branch kept.
- `--no-worktree` runs the slot from the repo root instead (single-agent mode).
